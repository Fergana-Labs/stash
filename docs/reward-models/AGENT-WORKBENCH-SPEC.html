Stash automatically assesses recorded agent behavior. A correction can improve the grader, change the agent’s instructions, or both. The trace viewer shows the evidence, the changes, and their use in later runs.

First users: Henry, Priyadarshan, SamFirst scope: our coding agents on Stash
The intended everyday experience

Keep using your agent. Stash checks its recorded work. When you correct a mistake, Stash prepares the relevant changes and checks them. Released instructions reach later runs, where we can inspect what the agent actually did.

No task-sorting chore.Existing run IDs and recorded events are enough to begin. Stash selects context automatically.
The trace stays central.Every assessment and proposed instruction can be traced to the exact messages, tool results, and feedback behind it.
Two things can improve.The grader’s decisions and the agent’s behavior have separate changes, checks, versions, and measurements.

This is the current product specification. It supersedes the earlier workbench and completed-task proposals, including their manual task-selection prerequisite. Earlier research notes remain background. All product behavior below is proposed unless explicitly identified as existing.

01

The product we are building

An automatic evaluation and instruction-update service with an inspectable trace viewer. The first integration uses our existing coding-session capture. JEV is the proposed grading technology; the product configures it with criteria and examples. Training new shared model weights is a separate research option.

The normal path is: configure a grader for an agent/repository → receive traces → attach assessments → collect occasional corrections → prepare and check changes → release versions → inspect later runs. A user does not assign every trace to tasks, prepare every comparison, or run training jobs to make this happen.

The main screens are Traces, Review, Graders, and Changes. Existing Skills remains the place to manage instruction files. Dataset exports, benchmark construction, and model-training controls sit under advanced research tools.

Automatic by default

Capture, assessment scheduling, context selection, feedback extraction, candidate changes, and available checks run in the background. Most traces require no human action.

Human input where it helps

State what good behavior means, correct a mistaken assessment, explain a new requirement, and resolve selected ambiguous cases. The product prepares the evidence for review.

Start with one supported harness and our own repository. Broaden integrations after this complete path works. Team members need explicit access to the same selected traces and review records; the existing owner-private reward-model views need that extension.

Direction drawn from the 6 October office-hours discussion. The detailed states, checks, and delivery sequence in this document are implementation proposals.

02

Configure a grader once, then refine it

The setup screen asks which agent/repository to assess, what behavior matters, and whether the user has examples of good and bad behavior. It drafts editable criteria and suggests examples from existing traces. An initial assessment does not require a fixed quota of human labels; its accuracy is marked unmeasured until independent review supports a quality estimate.

Setup fieldConcrete example
ScopeOur Codex runs in the Stash repository. Other repositories retain their own settings.
CriterionWhen reporting test results, distinguish recorded passes, recorded failures, and checks that were not run.
Reviewed exampleA test command exits with code 1; the agent says “all tests pass.” Human label: violates the reporting criterion.
Review preferencesSurface disagreements with my corrections, uncertain findings, and a small representative audit sample.
Change policyChoose the scope in which grader or instruction changes may be released, and whether release requires review or can happen automatically under configured rules.

A grader version includes the JEV/model configuration, prompt, criteria, and any examples supplied to the grader. Changing one creates a new version. A criterion can concern a particular action, an answer, or overall request fulfillment when sufficient evidence is present.

JEV integration is an implementation target. We need to verify its available inputs, outputs, cost, and latency. This spec does not assume that its numerical outputs are calibrated probabilities or that current production already exposes this interface.

03

What gets assessed, and when

New persisted trace events schedule background grading. Coalesce bursts of events so a tool call and its result can be assessed together. Assess a reporting claim once it is recorded and relevant outputs are available. A submission/end-of-turn marker can trigger an assessment of request fulfillment; an ambiguous stopping point produces a limited or insufficient-evidence result.

Long conversations do not have to end before useful assessments appear. Context selection retrieves the relevant requests, active instructions, earlier events, outputs, and captured files. Inferred grouping is editable, but never a prerequisite for capture or grading. If the selected context cannot support a verdict, the result must say so.

RecordRequired contents
Evaluation inputThe target event or event range; exact selected context; applicable criterion and grader versions; captured evidence references; evidence cutoff; omitted or truncated content.
Evaluation outputMeets / violates / insufficient evidence / not applicable; a reason; citations to captured evidence; raw model response and any numerical score.
Execution statusQueued, running, completed, or failed; timestamps and captured usage/cost. A failed grading request is not a negative verdict on the agent.

Each assessment concerns a named criterion. For example, a truthful “the test failed” can meet the reporting criterion while the code still fails a functional requirement. Do not turn one favorable assessment into a blanket declaration that the entire run succeeded.

Use separate records for a judgment based on evidence available at the time and a later retrospective judgment that includes review feedback. Reassessment appends history. Stable event and input revisions prevent duplicate work when the same upload is retried. Late-arriving evidence can schedule a new assessment without erasing the earlier one.

Assessment coverage, queue delay, and budget limits must be visible. An unassessed event is not implicitly approved. Step durations, token usage, and costs appear only when captured or explicitly estimated; missing fields remain unknown. Step timestamps do not establish full customer-system latency.

Terminology: these are rubric-based assessments of recorded actions and results. We are not claiming to know each action’s causal contribution to the final outcome.

04

The trace viewer is the main workspace

The list shows recent runs, owner, repository/harness where known, capture health, assessment coverage, flagged criteria, review state, and recorded usage. Search messages, tool output, and file paths. Opening a run shows its events beside an inspector. Findings jump directly to the relevant claim and evidence.

The inspector exposes the full grading input, raw output, criterion/version, evidence, and later corrections. You can comment on a finding, select a message, or inspect related changes without leaving the trace. No task-creation form appears before these actions.

05

What happens after a correction

A comment made in Stash already identifies its target. Corrections in the original agent conversation can also be detected and linked automatically, with their source role preserved. An extracted interpretation remains a proposal until the review policy accepts it. Agent-generated text or tool output must not silently become a human-approved label. Preserve whether acceptance came from a person or an automatic policy; automatic acceptance is not independent human review.

What the feedback establishesAutomatic preparationWhat changes
The judge missed an existing requirementCollect the target, criterion, evidence, and proposed corrected label.A candidate grader prompt/example change; possibly a bug report if context selection omitted the evidence.
The agent made a mistakeCollect the behavior and correction; draft a focused instruction diff.A candidate agent instruction. The grader may already be correct.
The requirement changedIdentify the new rule, scope, and proposed effective point.A new criterion version and, where appropriate, an agent instruction update.
The comment is ambiguous or disputedPrepare the conflicting evidence and interpretation for review.No silent release or unquestioned gold label.

One correction may produce both kinds of candidate change. Neither is mandatory for every comment. Show comment received → interpretation prepared → candidate change → checks → released / rejected / needs review, with links to the source and a readable explanation of the proposed change.

The Review screen prioritizes disagreements with feedback, uncertain findings, and high-impact failures. Include a representative sample so confidently wrong judgments can also be discovered. A score near 0.5 is a possible selection signal, not proof of calibrated uncertainty.

People may label a single assessment or a proposed A/B comparison. For pairs, show the common criterion and enough context to establish comparability; allow A, B, tie, insufficient evidence, or rejection of the pair. Similarity retrieval proposes examples—it does not establish which is better.

06

Improve the grader on saved evidence

The first improvement mechanism changes criteria, grader prompts, and supplied examples. It does not require a weight update. Use accepted feedback to prepare a candidate configuration, then compare candidate and current grader on the same target events, selected trace evidence, applicable criteria, and held-out human labels. Each grader receives its own versioned prompt and examples; preserve both complete rendered inputs.

Examples used to write the candidate prompt belong to development. Reserve other human-reviewed examples for evaluation, keeping duplicates and related continuations together. Stash manages this organization internally; occasional research audit of inferred groups is different from requiring every user to sort every trace.

The comparison screen shows counts and denominators, corrected errors, new errors, abstentions, captured cost, and the exact examples behind each result. Independently human-reviewed labels are distinct from automatically accepted interpretations. Repeatedly tuning against one reserved set can overfit it; refresh the release audit with independently reviewed later traces.

If the first correction arrives before independent reviewed examples exist, prepare the candidate and show quality check unavailable: no independent reviewed examples. Keep current grading active and collect review examples through the queue. Do not count the source correction as held-out evidence or require the user to build a dataset before continuing.

A new requirement needs labels under the new requirement. Do not silently reuse incompatible historical labels or describe an old run as violating a rule that had not applied. Historical reassessments under a new criterion must be explicitly labeled.

Releasing G2 changes future eligible grading. G1’s outputs and input snapshots remain inspectable. Grader changes and agent-instruction changes have separate release records. A rising score under a changed grader is not evidence that the agent improved.

Concrete check: on a frozen set of reviewed test-reporting examples, G2 catches more unsupported claims without introducing unacceptable false alarms. Every changed judgment opens the recorded claim, test output, and human label. The source correction used to create G2 is excluded from this independent result.

07

Change the agent’s instructions and verify delivery

A candidate skill contains exact proposed text, an editable diff, the source findings/corrections, intended repository/agent scope, and the version it would replace. The system can draft it automatically from accepted evidence. A saved draft must remain out of the agent’s active skill set.

“Release for agent use” is distinct from making a Stash skill publicly shareable. Reuse the existing editing and synchronization machinery, but add an explicit released version. Current generic skill synchronization is not itself a draft/release boundary.

State or observationWhat it means
Draft / checkedProposed instructions and available check results exist. Checks may cover scope, conflicts, or offline trials where supported; they do not automatically prove better real-world behavior.
Released / availableA specific version is available to the intended agent configuration. Store the exact content and release time.
Loaded in run RA harness receipt or captured context identifies the exact instruction text/version received by R. A file merely existing on disk is not enough.
Behavior observedA cited event shows the agent followed or violated the instruction.
Benefit measuredA specified comparison of later outcomes supports an improvement, with sample size and uncertainty.

Choose release policy once for a scope: Review changes or Auto-release under configured rules. The first internal slice supports automatic preparation/checking and explicit release. The target product adds automatic release for permitted change types after its gates are implemented and tested; ambiguous requirements and failed checks remain review items. This is staged delivery, not a requirement to operate every trace manually.

Rollback restores the selected released version for future eligible runs and records the change. It cannot erase instructions already received by a running session. Show pending delivery and any runs still using the previous version.

08

How we test a change to agent behavior

Grading saved records is not an agent rollout. A new prompt or skill changes what the agent does next. We need observed behavior from that changed agent to measure its effect.

Validation routeWhen it is validWhat it establishes
Isolated executionA disposable coding checkout or other authorized test environment supplies the required state and tools, with external actions controlled.Behavior and results in that environment. We can optimize candidate instructions against these executions.
Tool fixtures or simulationRecorded outputs match the actual calls/state, or an explicitly simulated environment supports the candidate’s new calls. Unsupported calls stop or invalidate the trial.A result under the fixture/simulator. Fidelity to real behavior still needs measurement.
Future ordinary workRelease a version to eligible naturally arriving runs, with version receipts and outcome monitoring. A comparative trial requires reliable per-run or per-cohort version assignment.Real observed behavior without repeatedly retrying the same customer request. A controlled comparison can estimate benefit across runs.

For internal dogfood, first verify delivery and inspect naturally occurring later coding work. To estimate benefit, compare current and candidate instructions across eligible future runs, predefine the outcome measures, and record assignment. Where possible, randomize assignment and keep the actor model and evaluation method fixed. If shared memory or global skill files contaminate the groups, label the result observational until isolation is supported.

Measure concrete outcomes: unsupported test-success claims, reviewer corrections, recorded check failures, tool errors, and cost where available. Use independent human audits or a fixed grader version for the comparison. One successful later run demonstrates use, not a general improvement.

Small text edits do not guarantee small behavioral changes. Simulation is an option to investigate, not a solved replacement for customer systems. The meeting’s proposals for tool interception and conservative online optimization therefore remain explicit engineering/research work.

What the product must retain

The normal product uses existing run/event identifiers. Optional inferred request or submission groups help particular assessments and research splits; they are not mandatory user-created records.

RecordRequired contents

AssessmentTarget references, exact input, criterion and grader versions, cutoff/omissions, raw output, verdict, evidence references, execution status.
Feedback/reviewOriginal comment or label, authenticated author/source, target, proposed interpretation, acceptance/review state, evidence and revision history.
Grader versionModel/provider configuration, prompt, criteria/examples, parent version, development/evaluation example snapshots, comparison report and release history.
Instruction changeExact text and diff, parent version, source feedback, scope, check results, release/rollback history, actual per-run load evidence.

Keep original predictions and comments; corrections create revisions. Captured code means the version actually recorded, not the current working-tree file. Missing snapshots stay visible. Apply workspace access to both raw traces and derived records; team review access does not implicitly authorize cross-customer training use.

11

Research direction and unresolved decisions

First research question: do corrections on recorded work make the configured grader more accurate on independently reviewed later work? Compare a fixed JEV configuration, an updated prompt/rubric/example configuration, and any trained probe or adapter on the same applicable criteria and held-out examples.

Second research question: do the resulting instruction changes improve subsequent agent behavior? That requires the execution and outcome comparisons in section 08. Better agreement between a grader and human labels alone does not answer it.

Shared reward-model weight training, adversarial robustness, and causal credit assignment remain research candidates. They are not prerequisites for trace ingestion, automatic grading, corrections, or instruction delivery. Accepted review examples can support that research without making dataset curation the everyday user interface.

The first complete demonstration

A real run arrives automatically. A grader makes an inspectable judgment. A correction produces a checked grader change and, when appropriate, a separate instruction change. A later real run receives the released instruction, and we can inspect its behavior.
